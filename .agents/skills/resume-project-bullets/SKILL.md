# 简历项目要点写作

## 核心目标

把项目经历写成容易阅读、方便面试展开的技术要点，而不是架构名词清单。

每条应让读者快速看出：

- 遇到了什么直接问题或业务背景
- 采用了什么核心方法
- 最终构建了什么能力或取得了什么结果

## 硬性要求

- 单个项目最多写六条，不能超过。
- 每条只承担一个重点，不把多个独立主题塞在同一条里。
- 整体业务链路和核心执行框架可以单独介绍，不强制采用问题解决结构。
- 其余条目必须采用“背景问题 → 核心方法 → 实现效果”的结构。
- 默认使用无序列表，不使用编号。
- 用户要求完整项目条目时，优先给齐六条；证据不足时减少条目，不编造内容补足。

## 写作流程

- 先核实项目事实、真实边界和用户想突出的重点，再组织语言。
- 将内容分为“整体链路介绍”和“问题解决型条目”，避免所有条目都写成同一种形式。
- 为问题解决型条目分别找出直接问题、核心方法和形成的能力。
- 合并细小的实现手段，只保留理解方案所需的关键技术。
- 检查每条是否有明确结果，避免停在“使用了某技术”。
- 调整句式，避免连续条目使用完全相同的开头。
- 最后核对事实，不为了增强表达而扩大生产规模、性能或稳定性结论。

## 背景怎么写

背景必须直接点明矛盾，不写空泛的“为了提升系统性能”“为了满足业务需求”。

优先使用具体场景：

- 多期任务同时处理时容易重复领取，worker 崩溃后任务可能卡住。
- 多个执行者同时调用外部付费服务，可能超过速率、并发或费用限制。
- 每个管理请求都启动新进程，带来额外延迟和资源开销。
- 多用户读取私有内容时，需要防止会话伪造和越权访问。

## 技术怎么写

- 只写支撑该条结论的核心方案，通常控制在两三类方法内。
- 不罗列字段、函数、配置项、状态值和过细实现步骤。
- 技术名称服务于问题，不为了展示词汇量堆叠。
- 保留能体现方案特色的关键技术词，其余细节留给面试展开。

过于细碎：

> 使用 PostgreSQL JSONB、ON CONFLICT、SKIP LOCKED、locked_by、locked_until、job_attempt、attempt_no 和 heartbeat。

更合适：

> 引入 PostgreSQL 持久化队列、租约管理和有界子进程调度。

## 结果怎么写

结果必须说明形成了什么能力，避免只写“提升效率”“优化性能”“增强稳定性”。

优先使用：

- 构建支持并发执行、故障接管和资源控制的任务处理链路。
- 构建供应商调用治理链路，避免超配额调用与费用失控。
- 将核心机制接入实际执行流程，实现断点恢复与异常结果保护。
- 构建私有内容访问链路，实现用户权限隔离与未授权访问拦截。

有真实指标时可以写数字，但必须注明测试环境、负载性质和统计范围。本地 fake 压测不能写成生产 QPS，组件吞吐不能写成外部供应商吞吐。

## 句式要求

不要连续使用“针对……”开头。根据内容自然变化：

- 为解决……，引入……，构建……
- 面对……约束，结合……，实现……
- 为降低……开销，将……，构建……
- 在……场景下，通过……，实现……
- 基于……完成……，支持……
- 实现……主链，串联……，支持……

语言变化不能破坏“问题—方法—结果”的逻辑。

## 事实边界

- 长驻进程不等于长连接，不把服务常驻写成网络连接设计。
- 支持 cron 调度不等于 cron 已经部署并长期运行。
- 集成某个框架的核心机制不等于自研该框架。
- 至少一次调度配合幂等与对账不等于分布式 Exactly Once。
- 本地测试通过不等于生产高并发或长期稳定性已经验收。
- 不用“显著提升”“大幅降低”等措辞，除非有对应测量依据。

## 自检清单

交付前逐条检查：

- 总条数是否不超过六条。
- 每条是否只有一个核心主题。
- 非整体介绍条目是否能清楚拆出背景、方法和结果。
- 背景是否是直接问题，而不是空泛口号。
- 技术是否足够简洁，没有堆叠细粒度名词。
- 结果是否明确写出构建的能力或实现的效果。
- 相邻条目的句式是否有变化。
- 每个结论是否都有项目事实支撑。

## 示例

不合格：

> 使用 PostgreSQL 持久化队列、唯一幂等键、SKIP LOCKED、job_attempt、租约、心跳、有界子进程和指数退避。

问题是缺少直接背景与结果，同时技术粒度过细。

合格：

> 为解决多期任务并行处理中的重复领取和故障恢复问题，引入 PostgreSQL 持久化队列、租约管理与有界子进程调度，构建支持多 worker 并发执行、崩溃接管和资源控制的任务处理链路。

不合格：

> 针对外部服务限流，针对高并发安全，针对预算控制，使用 Redis TIME、Lua、Hash owner、TTL 和 max_running。

问题是背景割裂、句式重复、技术堆砌，结果不清楚。

合格：

> 面对外部付费服务的速率、并发与费用约束，结合 Redis 分布式限流、并发控制和预算背压，构建多 worker 共享的供应商调用治理链路，避免超配额调用与费用失控。

## 输出方式

- 默认直接给出可放入简历的条目，不附加冗长写作讲解。
- 用户修改写法时，保留已经认可的内容，只调整指定问题。
- 用户只要求优化部分条目时，不无故重写其他条目。
- 面试展开材料与简历正文分开，避免把简历写成技术文档。
