# 面试讲解要点

## 当前阶段已经能讲的内容

### 1. 为什么先做 MVP 闭环

- 先保证注册、登录、上传、发布、Feed、详情可跑通。
- 先用最小数据模型把核心路径走通，再逐步扩展互动和异步链路。
- 避免一开始就把缓存、消息队列、统计表全部铺开，导致验证和调试成本过高。

### 2. 后端分层

- `cmd/api` 负责启动服务。
- `internal/domain` 放业务规则。
- `internal/infrastructure` 放 MySQL 和本地存储实现。
- `internal/transport/httpserver` 负责 HTTP 路由和响应。
- 这样后续加 Redis、MQ、SSE 时，不会挤压业务层。

### 3. 文件上传设计

- MVP 阶段先用本地磁盘。
- 通过 `multipart/form-data` 上传视频和封面。
- 上传后返回 `/media/...` 路径，再由静态服务暴露。
- 前端发布页先上传再发布，降低用户输入错误率。

### 4. 鉴权设计

- 登录后签发 JWT。
- 通过 `Authorization: Bearer <token>` 访问受保护接口。
- 点赞状态接口使用可选鉴权：匿名用户能看总数，登录用户能看到自己的 `liked` 状态。

### 5. Feed 和列表查询

- 最新流基于发布时间倒序。
- 作者作品列表基于 `author_id` 查询。
- 当前阶段直接用 MySQL，后续再引入游标分页和 Redis 时间线。

### 6. 点赞幂等设计

- `likes` 表使用 `(user_id, video_id)` 唯一约束。
- 点赞恢复已有记录，取消点赞写入 `deleted_at`，重复点赞/取消不会产生重复关系。
- 当前同步查询统计值，后续可以迁移为事件异步更新。

### 7. 评论设计

- `comments` 表使用软删除，列表只展示 `deleted_at IS NULL` 的评论。
- 评论发布需要登录，列表公开，删除时校验 `comment_id + current_user_id`，用户只能删除自己的评论。
- 评论内容在领域服务层做去空白和长度校验，避免把校验规则散落在 HTTP 层。
- 当前评论列表按 `created_at DESC, id DESC` 返回，后续可以扩展游标分页。

## 当前阶段已完成验证

- 后端健康检查可用。
- 注册、登录可用。
- 上传视频和封面可用。
- 发布视频、最新流和详情可用。
- 用户主页统计和作者作品列表已补上。
- 前端登录、发布、Feed、详情和用户主页已接上。
- 点赞接口和前端点赞状态交互已实现。
- 评论接口和视频详情评论区已实现，并完成 Go 格式化、测试和 Apifox 验证。
- 视频详情返回真实 `commentCount`，发表评论和删除评论后前端同步更新显示。
- 评论返回作者昵称，列表查询通过 `comments.user_id` 关联 `users.nickname`。

## 后续可继续讲的方向

- Redis 缓存视频详情和排行榜。
- RabbitMQ 做点赞、评论、关注异步化。
- SSE 实时通知。
- 分片上传和断点续传。
- Docker Compose 和 CI。
