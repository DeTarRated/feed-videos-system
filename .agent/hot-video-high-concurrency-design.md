# 热点视频高并发架构设计

## 1. 文档定位

本文档描述 `feed-videos-system` 面向热点视频场景的目标架构，重点解决：

- 大量用户同时点赞、取消点赞和评论造成的数据库写峰值。
- 热点视频详情、互动状态和评论列表的高并发读取。
- 缓存失效或 Redis 异常时的集中数据库回源。
- 高频互动下的热度计算、榜单更新和稳定分页。
- 消息重复、乱序、消费失败和中间件故障下的一致性与降级。

本文是目标设计，不代表当前代码已经全部实现。实施时应以本文的业务语义和一致性要求为准，通过压测确定连接数、批次大小、并发数和超时时间，不预设未经验证的 QPS 指标。

## 2. 设计目标与边界

### 2.1 核心目标

1. 将互动请求的瞬时峰值与 MySQL 写入能力解耦。
2. 将逐请求、逐行写库改为有界并发和微批次写入。
3. 让热点视频的主要读请求由 Redis 承载，并限制异常时的数据库回源。
4. 保证消息至少一次投递下的业务幂等、计数正确和乱序保护。
5. 通过增量热度窗口和热榜快照支持高并发 Feed 浏览。
6. 明确最终一致性、读己之写和故障返回语义。

### 2.2 设计边界

- 继续使用 Go、RabbitMQ、Redis 和 MySQL，不为了展示复杂度引入新的核心中间件。
- 采用单地域、可水平扩展的 API 与 Worker 架构，不设计跨地域多活。
- 不声称分布式 Exactly Once；使用至少一次投递、业务幂等和对账修复。
- 不追求所有接口强一致。互动链路接受短时间的最终一致性，核心内容最终必须持久化。
- 不把所有数据都放入缓存。MySQL 是最终事实源，Redis 是在线状态和查询视图。

## 3. 核心判断

热点视频会同时放大三类压力：

1. **写压力**：大量点赞、取消点赞和评论集中落到少量视频。
2. **读压力**：视频详情、点赞状态、评论列表和统计数据被反复读取。
3. **计算压力**：互动不断改变热度，如果每次请求都全量聚合和排序，数据库与计算成本持续上升。

因此，本项目的高并发主线不是“所有接口都使用缓存”，而是：

> 可靠异步接收互动命令，通过 Worker 微批次和幂等写入控制 MySQL 压力；通过 Redis 物化热点读状态并限制回源；通过分钟窗口和快照提供可持续更新的热榜。

## 4. 总体架构

```text

 Client
   │
   ▼
 Go API
   ├── 鉴权、参数校验、用户/接口限流
   ├── 生成 operationId、业务实体 ID 和操作版本
   └── 发布持久化 Command，并等待 Publisher Confirm
   │
   ▼

   ├── like.command.queue
   ├── comment.command.queue
   ├── retry queue
   └── dead letter queue
   │
   ▼

   ├── prefetch + 有界并发 + 微批次
   ├── 同业务键状态合并与按视频聚合
   ├── MySQL 事务、条件写入和批量写入
   ├── Redis Lua 原子更新在线状态、计数和热度
   └── 手动 ACK、失败重试和死信处理
   │
   ├──────────────► MySQL：最终事实源

                             热点读链路

                           │
                           ▼
                         MySQL

                     │
                     ▼
        Hot Rank Scheduler（Active / Standby）
          ├── Redis 分布式锁保证单活
```

## 5. Command 与 Event 语义

必须区分“请求系统执行操作”和“操作已经完成”。

### 5.1 Command

Command 表示系统已接受、但尚未完成执行的命令：

- `LikeCommand`
- `UnlikeCommand`
- `CommentCreateCommand`
- `CommentDeleteCommand`

点赞和评论创建都采用 MQ-first，不再由 API 逐条同步写 MySQL。

### 5.2 Event

Event 表示已经提交的事实：

- `LikeChangedEvent`
- `CommentCreatedEvent`
- `CommentDeletedEvent`

只有 MySQL 事务提交后，才能将对应操作视为业务事实。通知、审计等独立扩展可以消费这些事实事件。

如果未来采用“数据库先提交，再发布事件”的同步业务链路，应使用 Transactional Outbox 保证数据库与事件的一致性；当前 MQ-first 互动命令链路不依赖 MySQL Outbox，避免重新引入每次请求同步写库。

## 6. 统一命令模型

每条命令至少包含：

```json
{
  "operationId": "全局唯一操作 ID",
  "opVersion": "同一业务键内可比较的操作版本",
  "type": "like.create / like.cancel / comment.create / comment.delete",
  "actorId": 1001,
  "videoId": 2001,
  "commentId": "评论命令必须预生成",
  "content": "仅评论创建命令携带",
  "occurredAt": "API 接收时间"
}
```

字段职责：

- `operationId`：识别重复投递和客户端重试。
- `opVersion`：防止同一业务键的旧操作覆盖新操作。
- `commentId`：在 MySQL 插入前确定评论身份，支持幂等和前端即时展示。
- `occurredAt`：用于问题排查、延迟观测和业务排序辅助。

`opVersion` 的实现必须保证同一业务键内的新旧关系可比较，不能因为 Redis Key 过期或重启而静默回退为旧版本。初版实现需要明确版本生成与恢复方案；不能只使用一个会过期、丢失后从头计数的 Redis INCR Key。

## 7. API 写入链路

### 7.1 通用步骤

1. 完成鉴权、参数校验和接口限流。
2. 生成命令标识和业务实体标识。
3. 将命令通过长存发布通道发送到 RabbitMQ。
4. 使用持久化消息，并等待 Publisher Confirm。
5. Confirm 成功后返回“已接受”；Confirm 失败或超时返回可重试错误。
6. 客户端重试时复用原 `operationId`，由消费者完成去重。

### 7.2 响应语义

异步互动接口建议使用 `202 Accepted`，响应至少包含：

- `operationId`
- 目标状态或命令对象
- `status=pending`

点赞可以立即返回目标 `liked` 状态；评论创建可以返回完整评论对象、预生成的 `commentId` 和 `createdAt`。

这里的成功表示“系统可靠接收命令”，不表示“MySQL 已完成持久化”。

### 7.3 读己之写

由于 Worker 异步执行，用户刚操作后立即刷新可能短暂读到旧状态。前端应：

- 点赞后使用 API 返回的目标状态进行乐观展示。
- 评论创建后将返回的 pending 评论插入当前用户列表。
- 保留 `operationId`，用于失败提示、重试和状态查询。
- 后续读到更高版本状态后再替换 pending 数据。

该设计提供会话内的读己之写体验，不承诺所有客户端立即可见。

## 8. RabbitMQ 可靠性设计

### 8.1 基础配置

- Exchange 和 Queue 设置为 durable。
- 消息使用 persistent delivery mode。
- 发布端启用 Publisher Confirm。
- 消费端使用手动 ACK。
- 消费者设置合理 prefetch，禁止无界拉取。
- API 复用连接和发布通道，不为每条消息新建 Channel、重复声明 Exchange。
- 连接断开后执行有界重连，并恢复拓扑。

### 8.2 重试与死信

- 临时错误：Nack 或转入带延迟的重试队列。
- 可重试错误采用有限次数和退避策略，避免 tight loop。
- 超过重试上限进入 DLQ。
- DLQ 消息保留命令类型、业务主键、失败原因和重试次数。
- 提供人工或任务式重新投递与修复入口。
- 永久格式错误不能直接无限 requeue。

### 8.3 背压

- 通过 prefetch、Worker 并发、批次大小和数据库信号量限制消费速度。
- 通过队列深度和最老消息年龄识别消费能力不足。
- 达到系统保护阈值时，写接口返回限流或暂不可用，不无限接收无法处理的命令。
- MQ 确认失败时不能返回虚假的业务成功。

## 9. Worker 微批次处理

### 9.1 消费模型

Worker 使用有界 Worker Pool，按“批大小或最大等待时间”形成微批次：

- 达到批大小立即处理。
- 未达到批大小但达到最大等待时间也立即处理。
- 不在每条命令上执行完整数据库和缓存流程。
- 批大小、等待时间、prefetch 和并发数均通过配置与压测确定。

### 9.2 批内整理

- 点赞命令按 `(userId, videoId)` 分组，只保留最新有效操作版本。
- 评论创建命令不能合并，每条评论都是独立内容，但应合并为批量 INSERT。
- 按 `videoId` 聚合计数和热度增量，减少热点统计行与 Redis Key 的更新次数。
- 数据库批内按业务键排序后加锁或写入，降低死锁概率。

### 9.3 ACK 边界

目标处理顺序：

```text
接收批次
  → 批内合并与聚合
  → MySQL 事务提交
  → Redis 原子更新
  → 确认本批消息
```

MySQL 成功而 Redis 失败时，命令重新投递。数据库幂等防止重复业务写入，Redis 幂等防止重复计数。只有全部必要步骤成功后才 ACK。

## 10. 点赞与取消点赞

### 10.1 业务特点

点赞是状态命令，不是必须永久保留每次变化的内容记录。同一个用户对同一个视频的连续操作，可以按版本合并为最终状态。

### 10.2 MySQL 写入

点赞关系继续使用 `(user_id, video_id)` 唯一约束，并增加或保留：

- 当前状态或 `deleted_at`。
- `op_version`。
- `updated_at`。

Worker 根据当前行和命令版本执行条件 UPSERT：

- 新版本才允许覆盖旧版本。
- 重复命令不重复修改。
- 旧命令不能覆盖新状态。
- 根据真实状态变化计算每个视频的点赞数增量。
- 每个视频每批最多更新一次统计行。

必要的数据库去重记录应与业务写入、统计更新处于同一事务，避免只写关系但未更新统计。

### 10.3 Redis 更新

Lua 脚本以原子方式完成：

1. 检查操作标识或版本，拒绝已处理和过期操作。
2. 更新用户与视频的点赞关系。
3. 仅在状态真实变化时调整点赞数。
4. 仅在状态真实变化时记录有效互动热度。
5. 返回实际生效状态，供日志和后续处理使用。

### 10.4 替换全量脏集合同步

当前 `SMEMBERS 全量读取 + 批量 UPSERT + NOT IN 清理` 不适合作为热点视频的主要持久化方式：

- 集合越大，单次读取和网络传输越大。
- 大量未变化用户被重复写入。
- 大 `NOT IN` 增加 SQL 和数据库开销。

目标方案改为按命令批次增量写入。周期任务只承担低频对账和修复，不再每轮读取整个热点点赞集合。

## 11. 评论创建与删除

### 11.1 评论创建不能只靠同步逐行写库

热点视频下，多用户同时评论仍是高并发写。目标链路为：

```text
API 预生成 commentId
  → CommentCreateCommand 持久化到 MQ
  → Publisher Confirm 后返回 202
  → Worker 按 commentId 幂等
  → MySQL 批量 INSERT
  → 按视频聚合计数和热度
  → Redis 批量维护缓存
  → ACK
```

### 11.2 评论与点赞的差异

- 评论内容不可合并，每条有效评论都必须最终写入。
- 评论通过预生成 `commentId` 和数据库唯一约束实现幂等。
- 重复消息不能产生重复评论。
- 重复消息不能重复增加评论数或热度。
- 评论排序使用 `createdAt + commentId` 作为稳定次序。

### 11.3 评论删除

删除同样使用异步 Command：

- 命令携带 `commentId`、操作者和操作版本。
- Worker 校验作者并执行幂等软删除。
- 重复删除不重复扣减计数。
- 删除后维护评论详情、列表缓存和统计。

### 11.4 评论缓存维护

不能每来一条评论就简单删除热点视频首页缓存，否则会反复重建。Worker 应按批：

- 批量写入评论详情缓存。
- 批量追加或重建评论首页。
- 限制首页缓存长度。
- 每个视频每批只更新一次评论数。
- 每个视频每批只更新一次热度增量。

## 12. MySQL 数据职责

建议至少明确以下数据职责：

### 12.1 点赞关系

唯一键：`(user_id, video_id)`。

用途：保存最终点赞状态、操作版本和更新时间，支持条件 UPSERT 与按用户/视频索引查询。

### 12.2 评论

评论 ID 由 API 预生成，并在数据库保持唯一。

用途：保存内容、作者、视频、创建时间和软删除状态。

### 12.3 视频统计

使用 `video_stats` 一类独立统计数据，保存点赞数、评论数等可聚合字段。

用途：

- Worker 按批次聚合增量后更新。
- 缓存回源时直接读取计数，避免对关系表执行高成本 `COUNT(*)`。
- 为 Redis 统计重建和周期对账提供依据。

### 12.4 命令处理记录

对于不能仅靠业务状态自然去重的操作，可以记录 `consumer + operationId` 唯一处理记录。

处理记录必须与对应业务写入和统计更新处于同一事务。清理历史记录前，应确保业务主键和版本机制仍能阻止晚到消息造成重复效果。

## 13. Redis 数据拆分

### 13.1 视频元信息

示例：`video:detail:{videoId}`。

保存标题、作者、封面、播放地址和发布时间等相对稳定数据。互动变化不删除整个元信息缓存。

### 13.2 动态统计

示例：`video:stats:{videoId}`。

保存点赞数、评论数等高频变化数据，与视频元信息分开维护。

### 13.3 用户点赞状态

点赞关系是用户与视频的组合状态，不与公共视频详情混成一个缓存对象。

普通规模可以按视频保存集合；热点视频出现 Big Key 或迁移问题时，可按用户 ID 固定分片：

```text
like:users:{videoId}:{userId % N}
```

查询单个用户只需访问对应分片。分片数量通过配置确定，不在文档中宣称固定最佳值。

### 13.4 评论缓存

- `comment:detail:{commentId}`
- `comment:first_page:{videoId}`

详情和列表分别维护，避免异步删除和批量追加互相干扰。

### 13.5 热榜与快照

- 分钟热度桶：`hot:video:minute:{yyyyMMddHHmm}`
- 聚合榜单：`rank:video:hot:60m`
- 分页快照：`feed:hot:snapshot:{snapshotId}`

## 14. 热点读保护

### 14.1 正常读取

- 视频元信息、动态统计和用户点赞状态分别读取。
- 热榜页面优先批量 MGET，减少逐 Key 往返。
- 评论首页优先读缓存。
- 只有缺失数据才回源 MySQL。

### 14.2 缓存重建

- 单 API 实例使用 `singleflight` 合并相同资源回源。
- 多实例之间可使用短 TTL 的 Redis 重建锁，避免跨实例同时重建同一热点资源。
- 重建期间有旧值时优先返回旧值，并异步刷新。
- 不存在的数据使用短 TTL 空值缓存，降低无效 ID 的穿透查询。
- TTL 加随机抖动，避免大量 Key 同时过期。

分布式锁只用于控制重建，不应成为每次正常缓存读取的额外依赖。

### 14.3 有界数据库回源

Redis 异常时不能直接放开全部数据库查询：

- 使用数据库回源信号量限制并发。
- 配置数据库连接池、连接生命周期和查询超时。
- 统计回源次数、等待时间和失败率。
- 优先返回旧缓存或明确的降级结果。
- 对非核心动态数据允许暂时缺失，不无限阻塞请求。

### 14.4 回源查询

- 点赞关系使用唯一索引按用户和视频查询。
- 视频统计读取 `video_stats`，避免高成本聚合计数。
- 视频元信息按主键查询。
- 批量页面只回源缺失 ID，不重复读取已命中缓存的数据。

## 15. 热度排行

### 15.1 计分语义

热度定义为“最近 60 分钟内的有效互动活动分”，不是历史累计点赞数。

- 只有点赞状态真实从未点赞变为已点赞时，才记录一次点赞活动分。
- 重复消息、重复点赞和过期操作不加分。
- 只有评论实际插入成功时，才记录评论活动分。
- 重复评论命令不重复加分。
- 取消点赞不增加新的活动分；原互动随所属分钟桶自然退出窗口。

如果未来要表达“当前仍然有效的点赞贡献”，需要记录贡献所属分钟桶并在取消时冲销原桶，不能简单在当前时间随意扣减，否则窗口退出时可能重复扣减。

### 15.2 滑动窗口

- 互动写入当前分钟 ZSET。
- 聚合任务定时将新分钟桶加入总榜。
- 将 60 分钟前的分钟桶从总榜扣减并删除。
- 清理低分或无效成员，限制榜单规模。
- Worker 批内按视频聚合增量，减少逐命令操作。

### 15.3 拆分 Worker 与 Scheduler

当前 `cmd/worker/main.go` 同时启动消息消费、窗口聚合和清理任务。单 Worker 时没有问题，但为提升互动消费能力而扩容为多个 Worker 后，每个进程都会启动自己的定时器，导致同一分钟桶被重复加分或扣分。

这不是业务上需要多个聚合者，而是消费职责与调度职责绑定产生的副作用。目标结构拆分为：

```text
cmd/worker × N
  ├── 消费点赞和评论命令
  ├── 批量持久化与更新在线状态
  └── 写入分钟热度桶

cmd/scheduler × 2
  ├── Active：持有调度锁，执行窗口聚合与清理
  └── Standby：等待锁，不执行定时任务
```

Interaction Worker 可以独立水平扩容，Hot Rank Scheduler 通过主备单活避免重复聚合。Scheduler 短暂不可用只会延迟窗口滑动，不应阻塞互动命令消费。

### 15.4 Scheduler 主备单活

本项目不引入 Raft、etcd 或 ZooKeeper，也不自研分布式共识算法，只基于 Redis 分布式锁实现定时任务单活。

调度锁示例：

```text
Key：lock:hot-rank:scheduler
Value：每次持锁生成的唯一 ownerToken
```

工作流程：

1. Scheduler 使用 `SET key ownerToken NX PX ttl` 竞争锁。
2. 抢锁成功的实例成为 Active，开始执行窗口聚合和清理。
3. Active 在锁有效期内执行任务，并按配置周期续约。
4. 续约失败或发现锁已丢失时，必须停止后续调度，重新竞争成功后才能继续。
5. Standby 以有界间隔重试抢锁，不执行聚合。
6. Active 正常退出时，通过 Lua 校验 `ownerToken` 后释放锁，避免误删其他实例的锁。
7. Active 崩溃时无需人工选主，锁过期后由其他实例接管。

锁 TTL、续约间隔和抢锁间隔均为配置项，应结合单次任务耗时和故障注入确定，不宣称固定参数适用于所有环境。

分布式锁只降低并发执行概率，不能单独解决“任务已经生效，但进程在保存进度前崩溃”的重复执行问题，因此必须配合分钟桶幂等检查点。

### 15.5 分钟桶原子幂等检查点

分别记录分钟桶加入窗口和退出窗口的处理状态：

```text
hot:window:applied:add:{minute}
hot:window:applied:remove:{minute}
```

每个方向独立记录，避免“已加入窗口”被误认为“已完成过期扣减”。检查点保留时间应覆盖分钟桶重放与故障恢复周期，不能在接管时随意清空。

对某一分钟桶的聚合通过 Lua 原子完成：

1. 校验调度锁是否存在，且 Value 等于当前 Scheduler 的 `ownerToken`。
2. 检查该分钟桶、该操作方向的检查点是否已经存在。
3. 已处理则直接返回，不重复修改聚合 ZSET。
4. 未处理则将分钟桶分值加入或扣减聚合 ZSET。
5. 在同一 Lua 调用中写入检查点并返回处理结果。

原子性是关键：

- 先更新榜单、再单独写检查点，中间崩溃会导致接管后重复聚合。
- 先写检查点、再单独更新榜单，中间崩溃会导致永久漏算。
- Lua 执行成功但响应丢失时，重试会看到检查点并安全跳过。

分钟桶不能无界增长。如果单桶成员过多导致 Lua 执行时间过长，应限制单批处理规模并设计分段检查点，避免长时间阻塞 Redis；不能为了保留原子性而接受无界脚本执行时间。

### 15.6 设计边界

该机制应表述为“基于 Redis 分布式锁的 Scheduler 单活与故障接管”，而不是“自研分布式选主算法”。它解决的是本项目定时任务重复执行问题，不提供多地域容灾，也不替代 Redis 自身的高可用方案。

### 15.7 热榜快照分页

第一页：

1. 从聚合 ZSET 读取 Top N。
2. 创建有 TTL 的快照。
3. 返回包含 `snapshotId` 和 `offset` 的游标。

后续页：

1. 直接读取快照。
2. 按 offset 获取本页 ID。
3. 不再读取实时 Top N。
4. 不再遍历整个快照查找 `lastVideoId`。
5. 批量 MGET 页面数据，只回源缺失项。

快照过期或非法时开启新快照，并明确返回新的游标，不混用不同快照的排序。

## 16. 一致性与故障处理

### 16.1 一致性模型

- MySQL 保存最终业务事实。
- RabbitMQ 提供至少一次命令投递。
- Redis 保存可重建的在线状态和读视图。
- 数据库条件写入、业务唯一键和 Redis 原子脚本共同保证幂等。
- 周期对账用于发现与修复计数或状态漂移。

### 16.2 API 发布结果不确定

如果 API 在 Confirm 前超时或进程退出，客户端使用同一 `operationId` 重试。消费者必须能够处理“前一次其实已经发布成功”的重复命令。

### 16.3 RabbitMQ 不可用

- 写接口返回可重试错误或限流，不返回虚假的成功。
- 已缓存的读接口继续提供服务。
- 恢复后限制发布速率，避免重连后的瞬时流量再次压垮 MQ。

### 16.4 MySQL 不可用

- Worker 不 ACK 未完成的命令。
- 通过有限重试和队列积压形成背压。
- 不将失败命令直接全部打入无限 requeue。
- 读接口优先使用缓存，数据库回源必须有并发上限。

### 16.5 Redis 不可用

- 数据库已经提交但 Redis 未更新的命令通过重试完成。
- 热点读允许旧缓存或降级结果。
- 数据库回源由 singleflight、重建锁和信号量共同限制。
- 如果操作版本生成依赖 Redis，则对应写链路必须明确降级为不可用，不能绕过版本保护继续接收无序命令。

### 16.6 Worker 崩溃

未 ACK 消息重新投递。业务唯一键、操作版本和处理记录确保重复执行不会产生重复评论、重复计数或旧状态覆盖。

### 16.7 Scheduler 崩溃与接管

- Active 崩溃后调度锁自动过期，Standby 竞争成功后接管。
- Active 续约失败或失去锁时必须停止聚合，不能继续依赖之前的领导者身份。
- 接管者从分钟桶检查点判断哪些加入和移除操作已经生效，不能简单按当前时间跳过停机期间的桶。
- Lua 已生效但响应丢失时，接管者重试同一分钟桶会因检查点存在而跳过。
- 停机期间只延迟窗口聚合，互动 Worker 仍可继续写入分钟桶；恢复后按检查点补跑。
- 如果 Redis 整体不可用，调度暂停并暴露告警，不将窗口聚合转移到多个 Worker 上无协调执行。

### 16.8 DLQ 与修复

- 记录失败原因和重试次数。
- 提供按 `operationId`、评论 ID或用户视频键排查的能力。
- 修复后重新投递仍使用原命令身份。
- 对账任务只作为补偿，不替代正常幂等设计。

## 17. 限流、降级与资源控制

- 登录、发布、点赞、评论和关注继续使用用户或 IP 维度限流。
- 热点接口增加有界并发和超时，避免慢下游占满 API goroutine 与连接。
- 数据库、Redis 和 MQ 客户端均设置合理超时与连接上限。
- 不采用“中间件故障后自动切换到逐请求同步写 MySQL”的降级方式，这会把故障转化为数据库风暴。
- 写保护优先返回可重试错误；读保护优先旧缓存、部分数据或明确降级。
- 限流组件本身失败时需要明确策略，核心保护不能静默完全失效。

## 18. 可观测性

### 18.1 API 指标

- 请求 QPS、错误率、P95/P99 延迟。
- MQ 发布 Confirm 延迟和失败率。
- 各接口限流命中数。
- 数据库回源并发、等待时间和失败数。

### 18.2 MQ 与 Worker 指标

- 队列深度、最老消息年龄、消费速率。
- prefetch、实际并发和批大小分布。
- 批处理耗时、重试次数、DLQ 数量。
- MySQL 每批写入行数和事务耗时。
- Redis Lua 耗时和失败率。

### 18.3 缓存与热榜指标

- 各缓存命中率和回源次数。
- singleflight 合并请求数。
- 热点 Key 慢操作与大 Key 情况。
- 热度聚合延迟、检查点和失败次数。
- Scheduler 持锁实例、续约失败、锁丢失和主备接管次数。
- 分钟桶检查点命中、补跑和重复聚合拦截次数。
- 快照创建、命中和过期次数。

所有异步命令日志携带 `operationId`，并关联业务主键，使 API 接收、MQ 投递、Worker 处理和最终落库可以串联排查。

## 19. 压测与验证方案

### 19.1 单热点点赞写风暴

大量用户集中操作同一视频，观察：

- API 延迟和 Confirm 失败率。
- MQ 积压和最老消息年龄。
- Worker 批次吞吐。
- MySQL 实际写入次数和热点统计行冲突。
- Redis 计数与最终数据库关系是否一致。

### 19.2 单热点评论写风暴

验证：

- 评论是否按批插入，而非每请求逐条写库。
- 重复消息是否产生重复评论或计数。
- 评论首页缓存是否出现反复失效和重建。
- 最老命令延迟是否持续增长。

### 19.3 热点缓存失效读风暴

主动使视频详情或统计缓存失效，验证：

- 相同资源回源是否被合并。
- 多实例回源是否受控。
- MySQL 并发是否保持在上限内。
- 旧值和降级策略是否符合预期。

### 19.4 互动与热榜混合流量

持续写入点赞和评论，同时读取热榜多个页面，验证：

- 热度更新延迟。
- 快照内分页是否稳定。
- 后续分页是否仍访问实时榜单。
- 批量缓存读取是否减少 Redis 往返。
- 榜单聚合在多 Worker 下是否重复执行。

### 19.5 故障注入

至少覆盖：

- 发布 Confirm 超时后重试。
- MySQL 提交后 Redis 失败。
- Redis 更新后 ACK 失败。
- Worker 消费过程中退出。
- Scheduler 持锁期间退出、续约失败和主备接管。
- 分钟桶聚合已生效但响应丢失后的重试。
- 消息重复、乱序和多次重试。
- Redis 与 MySQL 分别短时不可用。

压测结论必须注明环境、数据规模、请求模型和统计范围。本地测试不能表述为生产容量证明。

## 21. 当前实现到目标结构的主要变化

保留并增强：

- API 与 Worker 双进程。
- RabbitMQ 异步削峰。
- Redis 点赞在线状态。
- Lua 原子状态处理。
- ZSET 分钟桶与 60 分钟窗口。
- 热榜快照。

重点替换：

- 每条消息新建 Channel → 受控复用发布通道。
- MQ 不可用仍可能返回成功 → Confirm 后接受，失败明确返回。
- 单 goroutine 顺序消费 → Worker Pool + prefetch + 微批次。
- 评论创建同步逐条写库 → 预生成 ID + 异步幂等批量 INSERT。
- 全量 `SMEMBERS + NOT IN` 持久化 → 增量条件写入 + 低频对账。
- `COUNT(*)` 回源 → `video_stats` 计数读取。
- 视频详情与统计数据混合缓存 → 元信息、统计和用户状态分离。
- 缓存失败直接回源 → singleflight + 重建控制 + 有界回源。
- Worker 扩容后窗口任务重复执行 → 独立 Scheduler 主备单活 + Redis 锁与原子幂等检查点。
- 快照分页仍读取实时 Top N → 快照游标直接分页。

## 22. 验收标准

设计实现完成后，至少满足：

1. API 只有在命令被 MQ 可靠接收后才返回已接受。
2. 同一命令重复投递不会产生重复评论、重复计数或重复热度。
3. 同一用户视频键的旧操作不会覆盖新状态。
4. 互动请求不会逐条同步写入 MySQL，Worker 能按批处理。
5. MySQL 和 Redis 任一阶段失败都可以通过重试收敛，不依赖人工发现常规故障。
6. 热点缓存失效时，数据库回源并发可观测且有上限。
7. 评论高频写入不会造成首页缓存逐条失效和重复重建。
8. Worker 水平扩容不会增加聚合次数；Scheduler 主备接管和任务重试不会造成分钟桶重复或遗漏聚合。
9. 热榜后续分页不读取实时榜单，同一快照内顺序稳定。
10. 压测和故障注入结果可以复现，并记录环境、指标和限制。

## 23. 项目重点表达

该项目最终应展示的不是单纯使用 RabbitMQ 或 Redis，而是一套围绕热点视频的完整设计：

> 以可靠异步命令承接互动写峰值，以微批次、状态合并和条件写入降低 MySQL 压力，以原子状态更新保证至少一次投递下的计数正确，以分层缓存和有界回源保护热点读，再通过增量热度窗口和快照分页支撑高并发 Feed 浏览。
